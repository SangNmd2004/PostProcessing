# ZC702 system integration

The existing QKD algorithm/decoder is unchanged. `rtl/top/qkd_pp_zc702.v` adds explicit Vivado interface metadata, 32-bit AXI addresses, full output TKEEP, and DMA-compatible input sidebands. It is reproducibly generated by `generate_wrapper.py`.

The integration uses the installed **ZC702 board preset**, PS DDR and MIO peripherals, **50 MHz FCLK0**, a common reset/clock domain, AXI GP0 for control and HP0 for DDR DMA. The stand-alone 70 MHz QKD synthesis is a separate result.

| Device | Base address | Paths |
|---|---|---|
| QKD IP | `0x43C00000` | original register offsets, full 32-bit writes |
| dma_ch | `0x40400000` | MM2S → CH; KEY → S2MM |
| dma_syn | `0x40410000` | MM2S → SYN |
| dma_pa | `0x40420000` | MM2S → PA_X; PA_Y → S2MM |
| dma_seed | `0x40430000` | MM2S → PA_SEED |

All four DMA IPs use **Simple mode, no scatter-gather, no Control/Status Stream**, 26-bit transfer length, 64-bit DDR masters and 32-bit input streams. The two receive streams are 64-bit. DRE is disabled; the supplied application aligns all DMA buffers to 64 bytes. PA_X and PA_SEED MM2S channels are started together before polling completion. RX channels are armed before any operation that can produce output.

IRQ_F2P bits 0..6 carry QKD, CH MM2S, CH S2MM, SYN MM2S, PA MM2S, PA S2MM and SEED MM2S, respectively. The initial functional test polls registers and does not validate IRQ delivery. Bits 7..15 are tied low.

`proc_sys_reset` has **active-low external and auxiliary reset inputs** in this design. External reset comes from PS FCLK_RESET0_N; auxiliary reset is tied HIGH (inactive), DCM locked HIGH and debug reset LOW. An earlier auxiliary LOW connection kept PL in reset and was rejected during the physical bring-up; its bit/XSA and reports are retained under `before_aux_reset_fix` / `INVALID_AUX_RESET` names and must not be programmed. `verify_bundle.py` checks the actual exported HWH polarity and constant connection before a board run.

## Build, from the repository root

```powershell
python .\syn\zc702\generate_wrapper.py
python .\firmware\zc702\gen_smoke_vectors.py
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\syn\zc702\run_system.ps1 -Stage validate
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\syn\zc702\run_system.ps1 -Stage synth
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\syn\zc702\run_system.ps1 -Stage implement
```

Run stages sequentially. Each Vivado process is limited to two threads. `validate` creates the project once; do not run it on top of an existing project. `all` resumes an existing validated project and runs synthesis/implementation sequentially. The project lives at `build/zc702/project/qkd_zc702.xpr`. These build commands do not program a physical board; the explicit board-test command below does.

`qkd_zc702_pre_synth.xsa` is only a preliminary hardware description. The deployable pair is `build/zc702/qkd_zc702.bit` and `qkd_zc702.xsa`, exported after routing and positive setup/hold slack. Bitstream generation also applies Vivado's normal DRC gates; no DRC severity or timing constraint is suppressed. If timing fails, the routed checkpoint and reports are retained, but bitstream/export stops.

```powershell
& 'D:\Xilinx\Vitis\2020.2\bin\xsct.bat' .\syn\zc702\build_smoke.tcl
```

Build the firmware only from the final XSA; it uses the matching generated standalone BSP. This command builds software and does not connect to JTAG or run it. Inspect `build/zc702/vitis/qkd_smoke/Debug/qkd_smoke.elf` and the build log before proceeding.

Verify the matching artifacts and record their SHA256 hashes after the build:

```powershell
python .\syn\zc702\verify_bundle.py
```

This checks the bitstream embedded in XSA against the external bitstream, DMA modes/widths/addresses, actual FCLK0, post-route timing, the BSP's XSA copies and DMA register definitions, application source copies, and the ARM ELF format. Results are recorded in `build/zc702/bundle_manifest.json`. Source hashes in the manifest record the reviewed source snapshot; they are not a signed build provenance record.

## Functional test boundaries

A generic UART receiver now supports changing CSV/QBER vectors without rebuilding the ELF. A physical campaign completed with **243/243 hardware results matching the reference**, including expected discards: 9 regression vectors, 84 native-CSV/code combinations, and 150 controlled-QBER trials. See [UART instructions](../../firmware/zc702_uart/README.md) and [measured CSV/QBER report](../../build/zc702/uart_runs/20261026T114819Z/REPORT.md). The UART campaign tests IR; its startup PA check still uses the original fixed vector.

`firmware/zc702/smoke_main.c` uses existing synthetic golden vectors (`data/tb`) and context **0**. Nine IR blocks check every attempt's status/iterations, reveals, every output key word, ERRCNT, expected discards, receive length, DMA errors and timeouts. The PA test compares all sixteen 64-bit output words. Cache flush/invalidate is included for the noncoherent HP0 path.

The physical ZC702 test passed on 2026-10-26 through JTAG and COM3 at 115200 baud, using the corrected reset connection and matching bitstream/XSA/BSP/ELF. Evidence: [UART log](../../build/zc702/board_runs/20261026T113309Z/uart.log), [machine-readable result](../../build/zc702/board_runs/20261026T113309Z/result.json), and [bundle manifest](../../build/zc702/bundle_manifest.json).

To repeat with the board powered and JTAG/UART connected, close other COM3 terminals and run from the repository root. This command resets and programs the board, starts the ELF, captures fresh UART output and writes a new timestamped result directory:

```powershell
python .\syn\zc702\run_board_test.py --port COM3
python .\syn\zc702\verify_bundle.py
```

The successful physical-board receipt is:

```text
QKD_ZC702_SELFTEST_START context=0 vectors=...
QKD_IR_VECTOR_PASS block=0 ...
...
QKD_IR_VECTOR_PASS block=8 ...
QKD_PA_VECTOR_PASS bits=4096
QKD_ZC702_SELFTEST_PASS blocks=9 pa=1
```

Any DMA error/timeout, output mismatch, wrong IP ID/config, or `SELFTEST_FAIL` is a failed test. Keep the full UART output. A compiler result, synthesis/PnR result, or XSA is not physical-board PASS. Even physical vector PASS proves functional transfer/computation only; the public fixed PA seed is not a TRNG or a live authenticated QKD session.

The original RTL retains four contexts, but Simple DMA does not store KEY TUSER in DDR. **Do not use the original multi-context driver for this initial board test.** General multi-context operation still needs reliable association between receive buffers and completion-context metadata. The original reference driver's blocking RX order is also not used by the supplied self-test.

Input TLAST/TKEEP are not interpreted by the original QKD packers: send exact full-word lengths. Wrong/short inputs can require resetting the accelerator and DMA. AXI-Lite byte writes are unsupported by the original IP; use aligned 32-bit MMIO writes.

References: [AMD AXI DMA PG021](https://www.amd.com/content/dam/xilinx/support/documents/ip_documentation/axi_dma/v7_1/pg021_axi_dma.pdf), [AMD Zynq embedded design tutorial 2020.2](https://xilinx.github.io/Embedded-Design-Tutorials/docs/2020.2/build/html/docs/Introduction/Zynq7000-EDT/2-using-zynq.html).

DRC has **0 errors, 1 warning, 12 advisories**. RTSTAT-10 concerns unused internal FIFO status/reset nets in the vendor AXI protocol converter. REQP-165/181 concern WRITE_FIRST RAMs inside vendor DMA FIFOs. They were retained and reported, not suppressed. The QKD RAMs are not the listed WRITE_FIRST FIFO instances. DMA/DDR operation passed the context-0 golden-vector self-test; interrupt delivery, concurrent contexts, throughput and long-duration operation remain unvalidated on hardware.

The 89 synthesis warnings include vendor modules' unused/trimmed ports and width differences for omitted optional AXI channels, plus empty vendor CDC-waiver endpoints in the synchronous configuration. There were zero synthesis critical warnings/errors. KEY TUSER is intentionally not stored by Simple DMA; the software limitation to context 0 is explicit above.
